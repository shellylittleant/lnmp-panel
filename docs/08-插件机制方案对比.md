# 08 插件机制方案对比

> 记录日期：2026-09-16
> 状态：已选择**方案二（Go 编译期插件）**，2026-09-16
>
> 落地方式：官方插件与核心在同一仓库，用 Go build tags 控制是否编译进去；正式发布的二进制带全部官方插件，运行时可启停。第三方插件需以 Go 源码形式提交合并后随官方发布。插件运行身份与面板一致（进程内无法降权），靠代码审查把关。

## 插件要承担什么

根据已定原则，插件至少要能做到：

1. 接入官方不支持的旧版本运行时（例如 PHP 7.4）：需要能安装软件、在"站点 PHP 版本"下拉框里注册一个新选项、提供对应 nginx 片段。
2. 增加核心之外的功能（例如 Redis 管理、翻译）：需要能有自己的页面、自己的设置、自己的后台逻辑。
3. 被第三方开发、独立分发、可能商业化闭源。

## 方案一：外部进程插件

插件是一个独立的可执行文件（任何语言）或脚本，放在约定目录，附带一个 `manifest.json` 声明名称、版本、需要的权限、提供的页面和钩子。面板启动时拉起插件进程，通过本机 Unix socket 上的 HTTP/JSON 通信。

| 优点 | 缺点 |
|---|---|
| 语言无关，第三方用 Python、Shell、Go 都能写 | 需要定义并长期维护一套稳定的插件 API |
| 插件崩溃不影响面板主进程 | 面板要管理插件进程的生命周期 |
| 安装、卸载、升级插件不需要重新编译面板 | 进程间通信比函数调用多一层开销（对面板这种低频操作可忽略） |
| 闭源商业插件天然可行 | 权限模型必须认真设计：插件以什么身份运行、能碰哪些文件 |
| 开源生态容易形成 | |

## 方案二：Go 编译期插件

插件是一个 Go 包，实现面板定义的接口，编译进主程序。装插件等于换一个新的面板二进制。

| 优点 | 缺点 |
|---|---|
| 最简单，无进程管理、无通信协议 | 用户装插件必须重新编译或下载官方预编译的组合包，无法自由组合 |
| 类型安全，接口变更编译期就发现 | 第三方插件必须开源且用 Go，否则无法编译进去 |
| 单一二进制，交付最干净 | 插件 bug 直接拖垮主进程 |
| | 与"开源 + 可商业化"目标冲突 |

## 我的建议：方案一为主，内部用方案二的接口

- 面板内部先定义一个 Go 接口，**官方核心功能（网站、防火墙、日志、PHP）自己也按这个接口实现**，作为进程内模块。
- 外部插件通过一个小适配层，把同一接口映射到 socket 通信。
- 这样接口只有一套，官方模块就是插件 API 的第一批用户，能保证 API 是够用的、被真实使用的，而不是纸面设计。

插件界面的做法：插件在 manifest 里用**声明式**方式描述页面（表单、表格、按钮），由面板统一渲染，风格一致，插件不需要写前端。确实需要复杂界面的插件，允许提供自己的静态页面嵌入。

## 需要你决定的

1. 采用方案一（含建议的混合做法），还是方案二？
2. 插件运行身份：与面板一样 root（能力最大，风险最大），还是默认降权、需要 root 的操作在 manifest 里声明并由用户安装时确认？我建议后者。
