## 3. 问题清单

### 严重（必须修复，修复后重审）

| 编号 | 问题 | 修复要求 |
|---|---|---|
| S1 | **A 的防火墙开机规则集被原样写成 B 的开机规则集。** `bundle.go` 导出 A 的 `/etc/lnmp-panel/nftables.conf`，`applyBundle` 直接 `WriteAtomic` 到 B 的同一路径。A 的规则里放行的是 **A 的面板端口和 A 的 SSH 端口**，两台机器的面板端口是各自随机生成的，几乎必然不同。B 下次重启时 `nftables.service` 加载这份规则，B 的面板端口被 drop，SSH 端口不同的话连 SSH 也没了。双容器测不出来是因为两边都固定用 18443。 | 防火墙不按文件同步，按**表单**同步：导出 A 的 `firewall_form`（开放端口、策略、CIDR 集合），B 收到后把 SSH 端口与面板端口替换成 B 自己的值，重新渲染成草稿，**不写开机文件、不加载**，在 B 的防火墙页显示"迁移带来的待应用规则"，由运维在 B 上走正常的应用与确认窗口。加测试：A、B 面板端口不同，同步后 B 的开机文件不含 A 的端口。 |
| S2 | **`mysqldump --all-databases` 会把 B 的 `mysql` 系统库一并覆盖，导入错误还被吞掉。** 导入后 B 的 `lnmp_panel` 账号变成 A 的密码，B 的面板从此连不上自己的 MySQL；root 认证方式也被 A 的覆盖。x86 官方 8.4 导到 arm64 的 Ubuntu 8.0 时系统表结构不同，导入会半途报错，而 `PeerApply` 里 `_, _ = run(...)` 把错误扔了，任务照样显示"完成"。另外 `dump_path` 由 A 指定、B 照单读取，且整份 dump 读进内存。 | 只导出面板纳管的库：`mysqldump --databases <mysql_databases 里的库>`；账号用 `SHOW CREATE USER` 与 `SHOW GRANTS` 逐个生成语句，`lnmp_panel`、`root`、`mysql.*`、`debian-sys-maint` 排除。B 侧导入路径固定为 B 自己的 `tmp/migrate-mysql.sql`，不接受 A 指定；用 `os.File` 流式喂给 `mysql`，不读进内存；导入失败要作为任务失败返回给 A；导入成功后两边删除 dump 文件。加测试：双容器各装 MySQL（arm64 走 Ubuntu 源），A 建库建用户，同步后 B 的面板仍能列库，B 的 `lnmp_panel` 仍能登录，A 的库与用户在 B 上可用。 |

### 一般（必须修复，随严重项一起重审）

| 编号 | 问题 | 修复要求 |
|---|---|---|
| G1 | **站点 conf 按 A 的渲染结果原样写到 B。** conf 里证书路径是 `tls/sites/<A 的站点 ID>/`，B 上同一站点的 ID 未必相同（B 已有站点时必然不同），B 的 `certificates` 行指向 `sites/<B 的 ID>/`，续期后写到新目录而 conf 还指着旧目录，证书过期都不知道。 | 非原文模式的站点在 B 上按模板重新渲染，不用 A 的 conf；原文模式才原样写入，并把其中的 `tls/sites/<旧 ID>/` 路径改写成 B 的 ID。证书文件按 B 的 ID 落盘。 |
| G2 | **`--delete` 会清掉 B 上原有的站点，`applyBundle` 也删掉 B 上不在包里的站点行，事先没有任何提示。** 完整同步是需求，但运维得知道。 | 预检返回 B 上已有站点数与站点 key，A 的界面在开始同步前显示"目标机已有 N 个站点将被替换"，必须勾选确认才能开始。 |
| G3 | **配对没有有效期，`authorized_keys` 里 A 的钥没有任何限制。** `validPeerToken` 不检查过期；握手后同一令牌永久有效，A 的 ed25519 钥在 B 上是无限制的 root 登录。 | `authorized_keys` 条目加 `from="<A 的来源 IP>",no-pty,no-agent-forwarding,no-port-forwarding,no-X11-forwarding`；配对记 `last_seen_at`，B 侧 7 天无活动自动拆掉授权段并作废令牌；A 的界面加"完成迁移"按钮，等价于取消。热备阶段需要长期配对时另起机制。 |
| G4 | **同步完成后 B 的状态是假的。** `php_versions.installed` 照抄 A 的值，B 没装 PHP 也显示已安装；任务显示"完成"，但站点 502。 | B 应用包后按本机二进制重算 `installed`；任务 detail 列出 B 缺什么（Nginx、PHP 各版本、MySQL），A 的界面显示这份清单，措辞为"文件与配置已同步，目标机还需安装：…"。 |
| G5 | 证书行 `ExpiresAt` 写成"现在加 30 天"，B 的续期任务会在 DNS 切过去之前每天尝试签发并失败。 | 用 `ssl` 包已有的 `leafNotAfter` 解析 PEM 取真实到期时间。 |

### 建议

| 编号 | 建议 |
|---|---|
| B1 | `Accept` 里 `peers.address` 取自请求体 `from`，改用 `RemoteAddr`。 |
| B2 | `/migrate/peer/*` 走令牌而跳过白名单是合理的，但这些路径应加简单限速（同 IP 每分钟 30 次），令牌 128 位够长，限速只是防日志刷屏。 |
| B3 | 双容器脚本让 B 用不同的面板端口和 SSH 端口，否则 S1 这类问题永远测不到。 |

### 复查（2026-09-17，commit `18aaddf`）

**结论：再次打回，只剩 S2 一项。** 其余全部通过。

审核者实际执行：`go vet`、`go test`（20 包）通过；执行者的双容器脚本（A 18443/22，B 28443/2222，两边 Ubuntu 源 MySQL）通过，`FIREWALL_BOOT_OK` 证实 B 的开机规则不含 A 的端口。代码核对：防火墙按表单同步并在 B 生成草稿；数据库只导纳管库；B 只读本机固定路径、流式导入、导入后删文件；授权钥带 `from=` 与 `no-pty` 等限制，7 天无活动作废；非原文站点在 B 重渲染；证书到期取自 PEM。

审核者在脚本里追加"用迁移过来的账号真的登录 B 的 MySQL"后重跑：**`migdb` 库到了，`migu` 账号没到，任务仍显示"完成"。** 执行者脚本对账号的断言只查了面板 SQLite 里的记录，没有登录 MySQL，所以没发现。

单容器实验定位根因：

| 步骤 | 结果 |
|---|---|
| `mysql -N -e "SHOW CREATE USER"` 的输出 | 密码哈希里含控制字符（`^E` `^O` `^C`）和被客户端转义的 `\\'` |
| 把这行原样回灌 | `ERROR 1064 ... syntax`；因为导入带 `--force`，**退出码仍是 0** |
| 改用 `HEX(authentication_string)` 生成 `IDENTIFIED WITH '<plugin>' AS 0x…` | 导入成功，用原密码登录成功 |

| 编号 | 要求 |
|---|---|
| S2-b | 账号导出改为从 `mysql.user` 读 `user, host, plugin, HEX(authentication_string)`，生成 `CREATE USER IF NOT EXISTS 'u'@'h' IDENTIFIED WITH 'plugin' AS 0x<hex>;`，不再解析 `SHOW CREATE USER` 的文本；授权仍用 `SHOW GRANTS`（纯文本，安全）。导入去掉 `--force`，任何错误即任务失败并把 stderr 带回 A。双容器脚本必须加上：在 B 上 `mysql -umigu -p<密码> -e 'select 1' migdb` 成功，且 B 的 `lnmp_panel` 仍能连接。 |

顺带一条不阻塞：A 的日志里出现 `调度 login_attempts.purge 失败：database is locked (SQLITE_BUSY)`，迁移期间写锁竞争超过 5 秒。`busy_timeout` 提到 15 秒，调度任务遇到 BUSY 记日志后下次重试即可。

界面重构（docs/14）尚未提交，与 S2-b 一起在下次重审看。
