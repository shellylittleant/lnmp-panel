# 10 容灾热备设计

> 记录日期：2026-09-16
> 状态：需求已确认，2026-09-16 第二次修订：**第一版全部人工操作，不做自动切换**

## 需求

A 机对外服务，B 机每 1 到 5 分钟同步 A 的全部内容。A 故障时，所有域名和内容切到 B 上直接可用，只损失几分钟数据。A 恢复后，B 把这段时间的数据反向同步回 A，补齐后再近乎无损地切回 A。

术语：A 为**主机**，B 为**备机**。任一时刻只有一台是主机，主机对外服务并接受写入，备机只接收同步。

## 可行性结论

可行。这是标准的"主备热备"模式，所有构件都是成熟技术，面板的工作是把它们编排成一个可靠的状态机。真正的难点有两个：

1. **切换时防止双写**（脑裂）。如果 A 只是网络抖动没真死，B 接管后 A 仍在接受写入，两边数据就分叉了，回切时无法自动合并。这是整个方案里唯一可能造成数据损坏的地方，必须在设计上封死。
2. **DNS 切换有传播延迟**。域名指向改了，用户的本地 DNS 缓存不会立刻更新，这段时间部分请求仍然去旧机器。

## 各类数据的同步方式

不同数据用不同机制，不能一刀切用 rsync。

| 数据 | 方式 | 延迟 | 说明 |
|---|---|---|---|
| 站点文件 | rsync 定时增量（默认 1 分钟），文件量大时改用 inotify 实时触发 | 秒到分钟 | 只传变化部分，百万级小文件全盘扫描会慢，所以留 inotify 方案 |
| MySQL | **MySQL 原生主从复制（GTID 模式）**，不是定时导出 | 通常 1 秒内 | 定时导出在 1 分钟间隔下对大库不可行；原生复制是持续的，且 GTID 让"反向同步、查漏补缺"变成数据库自带的能力 |
| Nginx / PHP / SSL / 防火墙配置 | 面板配置同步，复用迁移模块 | 变更即同步 | 主机上任何配置变更立即推送到备机 |
| PHP session、缓存 | 随站点文件同步，或接受切换后用户重新登录 | | 待确认取舍 |

MySQL 用原生复制的好处：备机数据库始终在线运行、始终追平主机，切换时不需要导入，且切换后反向复制（B 主 A 从）也是同一机制，A 追平 B 后再切回来，"按时间线查漏补缺"由 GTID 自动完成，不需要面板自己比对。

## 第一版原则：全部人工，不做自动

2026-09-16 确认：切换、回切、主备角色调整、DNS 修改，全部由运维人员手动完成。面板只提供按钮和状态，不做自动判定、不做自动接管、不对接 DNS API。

### 人工流程

**A 故障时**：运维登录 B 的面板，点击"启用主模式"。B 停止接收 A 的同步、MySQL 切为可写、启用全部站点。运维手动改 DNS 指向 B。

**A 恢复后**：运维登录 A 的面板，把 A 设为 B 的备机，开始从 B 同步。追平后，运维选择时机点击回切（或不回切，让 B 长期当主机也可以，A 变成备机，角色是对称的）。

### 预留的自动化接口

所有人工按钮背后都是内部 API（提升为主、降级为备、开始同步、查询同步状态、查询健康状态）。后期可接入 AI 或自动化程序调用这些 API 完成判定和操作。第一版只留接口，不实现任何自动逻辑。

## 人工切换后双写风险还剩多少

人工切换消除了"自动误判导致两台同时为主"这一主要场景。但还剩一个场景：

> A 因故障宕机后**自动重启**（云主机很常见），nginx 和 MySQL 随系统自启并接受写入。此时 B 已被人工提升为主，但部分用户的 DNS 缓存仍指向 A，这些用户的写入落到了 A 上。等运维发现并把 A 设为备机时，这部分写入已经与 B 分叉。

堵法很便宜，不是自动切换，是**自我保护**：

- B 被提升为主时，在 B 上记一个带版本号的角色记录。
- A 的面板启动时，若本地记录显示"我曾是主机且备机是 B"，先联系 B 询问角色。B 回答"我已是主"，A 就把 MySQL 设为只读、站点改为维护页，等运维处理。联系不上 B 则按原状态启动，不做猜测。
- 这一条只影响 A 自身，不会动 B，不会改 DNS，不会自动接管，与"全部人工"原则不冲突。

建议保留这一条保护。其余自动化一律不做。

## 以下为原自动化方案，保留供后期参考

## 切换（A 故障，B 接管）

1. **检测**：B 持续探测 A（多路径：面板心跳、HTTP 探测站点、MySQL 复制状态）。连续多次失败才判定故障，避免抖动误判。
2. **隔离**：B 接管前先尝试通知 A 进入"降级"状态（若 A 还能联系上）。A 降级后停止接受写入，把所有 HTTP 请求反向代理到 B。若 A 完全联系不上，跳过。
3. **提升**：B 停止复制，MySQL 切为可写，nginx 启用全部站点，B 成为主机。
4. **切 DNS**：通过 DNS 服务商 API 把所有域名的解析指向 B。
5. **通知**：告警到你。

DNS 传播期间，仍然打到 A 的请求：若 A 已死则失败（无法避免，除非用浮动 IP），若 A 只是降级则被代理到 B，用户无感。

## 回切（A 恢复）

1. A 恢复后**不允许自动变回主机**。A 启动时发现自己曾是主机但 B 已接管，自动进入降级状态：不接写入，请求代理到 B。
2. 面板把 A 配置为 B 的从机：文件从 B 反向 rsync，MySQL 反向复制，A 追平 B。
3. 追平后由你一键触发回切：B 短暂停写（几秒，让最后的数据落到 A），A 提升为主机，B 降级并代理到 A，切 DNS 回 A。
4. B 重新变回 A 的备机，回到初始状态。

停写窗口只有几秒，且期间请求被代理而不是失败，所以是"接近无伤"。

## 防双写的硬规则

- 任一时刻只有一台机器的 MySQL 是可写的，另一台强制只读。
- 主机身份由一个带版本号的"任期"记录决定，两台机器都存，版本大者为准。旧主机上线看到更大的版本号就自动降级。
- 自动接管默认**关闭**，只做检测和告警，由你一键确认接管。原因：两台机器互相判定对方失联时，没有第三方仲裁就无法区分"对方死了"和"我自己网络断了"，自动接管会制造脑裂。后期可加第三方仲裁点开启自动接管。

## SSL 证书

证书只在主机申请和续期，然后同步到备机。建议用 DNS-01 验证方式，不依赖 HTTP 请求打到哪台机器。

## 对"一个面板管一台机器"的影响

不变。A、B 各自的面板只管自己的机器，两者之间通过配对建立"主备关系"，复用迁移模块的配对令牌机制。

## 已确认细节（2026-09-16 第三次修订）

### 同步方向（2026-09-16 审核修订）

阶段 0 审核发现主机推送与备机拉取前后不一致，统一为**拉模型**：文件 rsync 由备机发起，MySQL 复制由备机连主机 3306（协议上只能如此），配置由备机定时拉取。因此：

- **主机**防火墙放行备机 IP 访问 SSH、3306、面板 API。
- **备机**防火墙只放行主机 IP 访问面板 API（供自我保护查询角色）和运维 IP 访问面板端口。80/443 对公网开放但只回 404。

下节"只允许主机 IP 访问同步相关端口"按此理解。

### 备机的对外状态

- 备机**完全不对外服务**。80/443 端口开放但 nginx 只有一个兜底 server，对任何域名、任何路径一律返回 404。
- 防火墙（nftables）白名单模式：只允许主机 IP 访问同步相关端口（SSH/rsync、MySQL 复制端口、面板 API），以及运维 IP 访问面板端口。其他来源全部丢弃。
- 注意：面板端口必须对运维可达，否则故障时无法登录 B 点击"启用主模式"。安装时要求填写运维 IP 白名单。
- 备机不申请证书，证书从主机同步而来。

### 登录态

- 切换后 PHP session 丢失，用户需重新登录，**可接受**。
- 用户账号密码存在站点数据库中，随 MySQL 复制同步，**不会丢失**。
- 面板自身的管理员账号各机独立，B 面板有自己的登录密码，与 A 无关。

### 模式

主备，不是双活。任一时刻只有一台对外。

### 数据规模与同步间隔

各类数据的承载能力不同：

| 数据 | 承载能力 | 说明 |
|---|---|---|
| MySQL | 无实际上限 | 原生复制按事务日志传输，与库大小无关。只有首次建立复制需要全量拷贝，用 MySQL 自带的 clone 插件，几百 GB 也可行 |
| 配置 | 无上限 | 体积极小 |
| 站点文件 | 瓶颈在**文件数量**，不在总体积 | rsync 每轮要扫描整棵目录树比对，扫描耗时与文件数成正比，传输量只与变化部分有关 |

站点文件的经验值（普通云盘）：

| 文件总数 | 一轮扫描耗时 | 适合间隔 |
|---|---|---|
| 10 万以内 | 几秒 | 1 分钟 |
| 100 万左右 | 30 秒到 2 分钟 | 5 分钟 |
| 数百万以上 | 数分钟以上 | 需要 inotify 实时触发，或按站点拆分错峰同步 |

**采用自适应间隔**，不需要你预先判断规模：

1. 默认目标间隔 1 分钟。
2. 每轮同步结束才开始下一轮，绝不重叠。
3. 若一轮耗时超过目标间隔，面板自动把间隔拉长到"上一轮耗时 + 余量"，并在界面上显示实际间隔和落后时间。
4. 超过 5 分钟仍追不上时告警，提示拆分站点或启用 inotify（后期功能）。

这样小规模自然是 1 分钟，大规模自然退化为你说的"5 分钟集中同步"，中间不需要人调。

## 已关闭的问题

J1、J2、J4 因"全部人工"不再需要。J3、J5、J6、J7 已由上节回答。

- **J1.** 域名解析用的是哪家 DNS 服务商？（Cloudflare、阿里云、DNSPod、其他）切换 DNS 需要对接其 API，第一版只做你在用的。
- **J2.** A 和 B 是否在同一云厂商的同一地域？若是，可用浮动 IP 代替 DNS 切换，没有传播延迟；若不是（真正的异地容灾通常不是），只能走 DNS。
- **J3.** 站点和数据库的规模量级？（文件总量、文件数、数据库大小）决定 rsync 定时是否够用，以及首次同步耗时。
- **J4.** 是否接受"自动检测告警、手动一键接管"作为第一版？我强烈建议接受，理由见防双写一节。
- **J5.** 备机 B 平时是否完全不对外服务？（我默认是，最简单）
- **J6.** 切换后用户登录态丢失是否可接受？不可接受则要同步 session 文件，代价是同步频率要更高。
- **J7.** 明确一点：本方案是**主备**，不是**双活**。两台同时对外写入、自动合并冲突，复杂度是另一个量级，不在范围内。请确认你不需要双活。
