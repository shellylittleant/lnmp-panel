# 01 可行性评估与待确认问题

> 记录日期：2026-09-16
> 状态：评估完成，问题待逐一解答

## 一、可行性结论

**可行，且难度明显低于通用面板。** 理由：

1. 固定 Ubuntu + 固定版本组合，意味着安装、配置文件路径、服务管理命令全部可以写死，不需要抽象层。这是通用面板里最重的一块代码，直接省掉。
2. 五项核心功能中，四项本质上是"读写几个配置文件 + 调用几个系统命令"：
   - 网站配置 = 生成 nginx server 块 + `nginx -t` + `systemctl reload nginx`
   - 防火墙 = 封装 `ufw` 或 `nftables`
   - PHP 管理 = `apt install php8.x-扩展名` + 改 php.ini + 重启 php-fpm
   - 监控 = 定时读 `/proc`、`systemctl`、nginx/php-fpm status 接口，存本地
3. 真正有工程量的只有两处：**一键迁移**和**监控数据的存储与展示**。其余都是薄封装。

### 粗略工作量判断

| 模块 | 难度 | 说明 |
|---|---|---|
| 面板骨架（登录、鉴权、API、前端） | 中 | 一次性基础设施 |
| 环境安装（一键装 LNMP） | 低 | 固定版本，脚本化 |
| 网站管理 + nginx conf | 低-中 | 模板化生成，难点在伪静态规则的表达 |
| 防火墙 | 低 | 薄封装 |
| PHP 扩展与配置 | 低 | 薄封装 |
| 监控与统计 | 中 | 采集简单，存储和图表需要设计 |
| 一键迁移 | 中-高 | 涉及文件、数据库、配置、证书的一致性打包与恢复 |
| 插件机制 | 中 | 需要提前定接口，否则后期难改 |

## 二、风险点

1. **"最高版本"是移动目标。** Ubuntu 每两年一个 LTS，PHP 每年一个大版本，MySQL 也在推进。需要明确"最高版本"的定义和跟随策略，否则面板本身会被自己的原则绑死。
2. **Ubuntu 官方 apt 源的版本滞后于上游。** 例如 Ubuntu 自带的 PHP 通常比官方最新版落后一到两个小版本。想要"最高版本"就必须引入第三方源（PHP 的 Ondřej Surý PPA、MySQL 官方 apt 源、Nginx 官方源），这会带来对外部源的依赖。
3. **迁移是跨机器操作。** 一旦涉及跨机器，就要处理认证、传输、断点、目标机预检等问题，这块会是整个产品里最容易出 bug 的地方。
4. **面板本身以 root 运行。** 面板的安全性直接等于服务器的安全性，登录鉴权、暴露面控制必须优先设计，不能后补。
5. **插件接口定早了容易错，定晚了核心要返工。** 建议核心先只留钩子位置，第一批插件之前再冻结接口。

### A. 版本与环境策略

> 2026-09-16 更新：A1、A3、A4、A5 已由"保留三代"原则统一回答，见 [02-版本策略.md](02-版本策略.md)。该文档中仍有两处细节待确认。A2、A6 仍待解答。

- **A1.** "Ubuntu 最高版本"指最新 **LTS**（目前 26.04），还是最新的**非 LTS** 半年版？我建议只跟 LTS，非 LTS 生命周期只有 9 个月。
- **A2.** 新 LTS 发布后，面板是否需要提供"就地升级"能力？还是只在新机器上支持新版本，老机器靠"一键迁移"过去？（后者更符合你的简单原则）
- **A3.** 软件版本来源：用 Ubuntu 自带 apt 源（版本稳定但滞后），还是用官方/第三方源（版本最新但多一个外部依赖）？这决定了"最高版本"的实际含义。
- **A4.** "msq" 我理解为 **MySQL**，请确认不是 MariaDB。MySQL 版本线选 **8.4 LTS** 还是跟随最新的创新版（Innovation Release）？我建议 8.4 LTS。
- **A5.** PHP 是**同一台机器只装一个版本**，还是允许 8.1 / 8.2 / 8.3 / 8.4 **多版本共存**、每个站点各选一个？多版本共存是宝塔的常见用法，但会增加复杂度。
- **A6.** 面板是否负责**从裸系统一键安装 LNMP**？还是假设环境已存在，面板只做管理？

### B. 一键迁移

- **B1.** "系统一键迁移"的具体含义是哪一种？
  1. 站点级迁移：把某个/全部站点（文件 + 数据库 + nginx 配置 + SSL 证书）从 A 机搬到 B 机。
  2. 从宝塔面板迁移过来。
  3. 整机备份与还原（备份到本地或对象存储，再在新机恢复）。
- **B2.** 迁移的传输方式：A 机和 B 机**直连**（SSH/rsync），还是经由**中转存储**（S3/OSS/rclone 等）？
- **B3.** 迁移是否需要**增量/断点续传**，还是全量搬一次就够？
- **B4.** 是否需要独立的**定时备份**功能？它和迁移共用一套打包逻辑，顺手就能做，但要确认是否在范围内。

### C. 防火墙

- **C1.** 底层用 `ufw`（简单，Ubuntu 默认）还是直接操作 `nftables`（更灵活，更复杂）？我建议 `ufw`。
- **C2.** 是否需要 **IP 黑白名单**、**fail2ban 式的自动封禁**（如 SSH 暴力破解防护）？
- **C3.** 你的服务器是否在云平台上（有云安全组）？如果是，面板的防火墙只管本机层面即可。

### D. 监控与统计

- **D1.** 监控哪些指标？我预设的清单：CPU、内存、磁盘、网络流量、负载、nginx 请求量、php-fpm 进程状态、MySQL 连接数与慢查询。需要增删吗？
- **D2.** 数据保留多久？（例如 7 天原始数据 + 90 天按小时聚合）
- **D3.** 是否需要**告警**？如需要，通知渠道是什么（邮件、Telegram、企业微信、Webhook）？
- **D4.** "数据统计"是否包含**站点访问统计**（PV/UV/来源，基于 nginx access log 分析）？这个工作量比资源监控大不少。
- **D5.** 存储用面板内嵌的 SQLite 就够，还是希望能对接 Prometheus 之类的外部系统？

### E. 网站配置

- **E1.** 除了 301 和伪静态，是否需要：**SSL 证书自动申请与续期**（Let's Encrypt）、**反向代理**、**HTTP/2 与 HTTP/3**、**访问限制（basic auth、IP 限制）**、**防盗链**？请勾选需要的。
- **E2.** 伪静态规则是**内置常见模板**（WordPress、ThinkPHP、Laravel 等）+ 自定义文本，还是只提供自定义文本？
- **E3.** 是否允许用户**直接编辑完整 nginx conf** 作为兜底？允许的话面板需要处理"手改后面板界面与文件不一致"的问题。
- **E4.** 数据库管理是否在范围内：创建库/用户、改密码、导入导出？是否需要内嵌 phpMyAdmin 或类似工具？

### F. PHP 管理

- **F1.** "加载插件"是指安装 PHP **扩展**（redis、imagick、gd 等）吗？安装方式只走 `apt`（简单可靠），还是也支持 `pecl` 编译（可装任意扩展但慢且易失败）？
- **F2.** php.ini 是提供**常用项表单**（上传大小、内存限制、超时、opcache），还是只提供文本编辑？

### G. 面板本身

- **G1.** 后端语言偏好？我建议 **Go**：编译成单文件二进制，无运行时依赖，`systemd` 一条服务跑起来，最符合"简单"原则。备选 Python 或 Node，但需要在目标机上装运行时。
- **G2.** 前端偏好？是否有你熟悉的框架（Vue / React / 纯 HTML+HTMX）？
- **G3.** 面板的暴露方式：直接监听公网端口（需自带 HTTPS + 强鉴权），还是只监听本机、通过 SSH 隧道访问（最安全，但每次访问要先建隧道）？
- **G4.** 是否需要多用户？还是只有一个管理员账号？是否需要二次验证（TOTP）？
- **G5.** 一个面板管理**一台**服务器，还是一个面板集中管理**多台**服务器？这影响架构根本设计，也影响迁移功能的形态。
- **G6.** 界面语言只做中文，还是要预留国际化？
- **G7.** 该产品是**自用**还是准备**开源/分发**给他人？这决定了文档、安装脚本、错误提示的打磨程度。

### H. 插件机制

- **H1.** 插件用什么形式？候选：
  1. 独立可执行文件 + 约定的 JSON/HTTP 接口（语言无关，隔离好）
  2. Go 插件包，编译进主程序（最简单，但改插件要重新编译主程序）
  3. 脚本（Shell/Python）+ 面板提供的 API
- **H2.** 插件是否需要有自己的界面页面？还是只提供后台能力，界面由核心统一渲染？
