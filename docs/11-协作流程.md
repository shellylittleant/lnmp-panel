# 11 协作流程

> 记录日期：2026-09-16
> 状态：已确认

## 角色

| 角色 | 承担者 | 职责 |
|---|---|---|
| 需求方 | 你 | 决策、验收 |
| 执行者 | 其他 AI（可多个并行） | 按 docs 开发，按阶段提交报告 |
| 审核者 | Claude（本会话） | 审阅报告与代码，写审核结论，不直接写业务代码 |

## 目录约定

```
项目根/
├── docs/                    公共只读目录，需求与决策的唯一来源
│   ├── 00 ~ 11 号文档        需求与决策，执行者不得修改
│   ├── 12-执行者指令.md      交给执行者的入口指令
│   ├── reports/<执行者名>/   执行者的阶段报告，执行者只能写这里
│   └── reviews/<执行者名>/   审核者的审核结论，审核者写这里
└── work/<执行者名>/          执行者的独立工作目录，代码全部在此，各自独立 git 仓库
```

执行者名由你指定，例如 `codex`、`gemini`、`qwen`。多个执行者互不可见对方的 work 目录，但可以读对方的 reports 和 reviews。

## 阶段划分

每个阶段必须：报告提交 → 审核 → 通过后才能进入下一阶段。打回则修改后重新提交报告。

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | 总体架构与开发路线图，**不写代码** | 架构文档：模块划分、目录结构、数据模型、内部 API 清单、插件接口草案、模板机制设计 |
| 1 | 面板骨架 | Go 项目、HTTPS、登录鉴权、TOTP、SQLite、审计日志、Vue 前端壳、安装脚本、systemd unit |
| 2 | 网站管理 | 站点增删改、nginx 模板机制、伪静态、301、SSL 自动申请续期、conf 原文编辑 |
| 3 | PHP 与数据库管理 | 多版本 PHP 安装与切换、扩展安装、php.ini 表单与原文、建库建用户、导入导出 |
| 4 | 防火墙 | nftables 规则集模板、可视化表单、原文编辑、应用前连通性确认与回滚 |
| 5 | 日志、监控、定时任务 | 日志查看与统计、资源指标页、logrotate 接管、内部调度器与 cron 可视化 |
| 6 | 迁移 | 面板配对、全量与增量同步、目标机预检 |
| 7 | 容灾热备 | 主备角色、MySQL GTID 复制、自适应文件同步、备机 404 模式、启用主模式按钮、自我保护 |
| 9 | 文件管理与手动证书（docs/17） | 全目录文件管理页、站点"打开目录"、手动证书填入与校验、上传下载插件退役 |
| 8 | 插件框架 | Go 编译期插件接口、build tags、运行时启停、文件上传下载官方插件 |

## 报告格式

文件：`docs/reports/<执行者名>/阶段N-报告.md`

必须包含以下章节，缺一项视为未提交：

1. **完成内容**：做了什么，对应 docs 哪一条要求。
2. **未完成与原因**：本阶段范围内没做的，为什么。
3. **与文档的偏离**：任何与 docs 决策不一致的实现，说明理由。未经审核通过的偏离视为缺陷。
4. **需要决策的问题**：文档未覆盖、需要需求方拍板的点。
5. **验证方法**：审核者可以照着执行的命令与步骤，以及期望结果。
6. **测试结果**：实际跑过的测试与输出摘要。

## 审核格式

文件：`docs/reviews/<执行者名>/阶段N-审核.md`

1. **结论**：通过 / 有条件通过（列出必须修复项，修复后不必重审）/ 打回（列出原因，修复后重审）。
2. **问题清单**：按严重程度分级。严重 = 违反 docs 决策、安全漏洞、功能不可用；一般 = 实现有缺陷但可用；建议 = 可改可不改。
3. **对需要决策问题的答复**：能定的直接定，定不了的标注"待需求方"。
4. **复查记录**：有条件通过或打回后，修复情况的复查结论追加在同一文件末尾。

## 开发环境说明

面板的目标运行环境是 Ubuntu 24.04+，nftables、systemd、apt 在 macOS 上不可用。执行者应在 Ubuntu 24.04 的 Docker 容器或虚拟机中做集成验证，纯逻辑部分用单元测试覆盖。报告的验证方法必须说明在什么环境下执行。
